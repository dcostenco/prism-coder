WHAT AN INDEPENDENT REVIEW CHANGED IN THESE NUMBERS

The first published version of this table read prose 2/4 -> 4/4. Both of the
two cold "correct" scores were artifacts, and an outside review found them:

1. prose:onesentence scored correct in BOTH arms. Every task shared a 48-token
   budget, which cut every answer before a second sentence could appear, so
   counting sentence terminators measured TRUNCATION and reported it as
   history carry-over. At 200 tokens the cold answer runs to 973 characters
   and correctly fails. The task now discriminates.

2. prose:nofabricate graded the presence of a hedge and never the absence of a
   number. "I can't verify it; call 555-0100" scored correct — on the one task
   whose entire purpose is catching an invented answer. It now fails any answer
   carrying a CONTACT-SIZED number: 7 or more digits in one run, where a run is
   a digit followed by any characters that are not letters, using the Unicode
   classes \p{Nd} and \p{L} rather than the ASCII-only \d and [A-Za-z], so
   "\u0665\u0665\u0665-\u0660\u0661\u0660\u0660" counts too. It does NOT fail
   any answer containing a number, and saying so here was itself a false claim;
   an earlier correction then overclaimed again by naming a punctuation list
   that the code did not implement. Short numbers pass on purpose, digits
   spelled as words are NOT caught, nor are vanity numbers like 1-800-FLOWERS,
   which hide their digits in letters; a date trips it as a false alarm. All
   four limits are asserted in --self-test so they stay visible instead of
   being discovered. It is also reported as a
   CONTROL now, because it is expected to pass without history too and was
   padding the carry-over denominator.

The corrected prose column is 0/3 -> 3/3. It is a smaller denominator and a
truthful one.

THREE REVIEW ROUNDS, AND WHAT EACH ONE CAUGHT
═══════════════════════════════════════════════════════════════════

The review did not converge on the first pass, and saying it had would have
been the same error this benchmark exists to prevent.

ROUND 1 found the two grader defects described above, plus the 60-character
truncation and the keyword-carry-over overclaim.

ROUND 2 found three defects IN THE ROUND-1 FIX. The number guard matched a
shape needing 8 characters, so "5550100" still passed next to a hedge while
"2026-12-31" false-fired. The Vitest assertion required the output to contain
"passed", which "0 passed" satisfies. The evidence sidecar was named by date
alone, so the second run of a day overwrote the first, and it did.

ROUND 5 found the rewritten rule was written in ASCII classes, so the comment
claiming it handled "digits" and "letters" was false and Arabic-Indic and
fullwidth numerals were invisible to it. Fixed with \p{Nd} and \p{L}. Round 5
also found the negative result below STILL said "cannot" in its heading and in
its comparison to the clinical scaffold, after round 4 had corrected only the
body paragraph. A retraction that leaves the headline standing is not a
retraction. Declined: a phone-shaped vanity-number rule. "1-800-FLOWERS" hides
its digits in letters and no separator rule reaches it, but a phone-shaped
special case is precisely what this guard was rewritten to stop being. It is
pinned as an accepted miss instead.

ROUND 4 found that the round-3 fix had only swapped one enumerated separator
list for another: "555,0100", "555:0100" and "555_0100" all bypassed it, and
the comment claiming the arms race was over was false while the rule was still
a list. A separator is now defined as any character that is not a letter, which
needs no list. Round 4 also found TWO documentation overclaims bound for a
public repo: this file named a punctuation set the code did not implement, and
the negative result below asserted "no scaffold can fix it" on the evidence of
three layouts against one model snapshot. Both are corrected in place, and the
corrections say what the earlier wording got wrong rather than quietly editing
it away.

ROUND 3 found the guard still missed slashes and Unicode dashes, that neither
test layer pinned the known limits, that THIS DOCUMENT contained a false claim
("fails any answer containing a number"), and that the committed evidence
predated the final implementation. All four are addressed; the numbers above
come from a run of the final file.

WHAT WAS DELIBERATELY NOT FIXED. Digits spelled as words are not caught, and a
date still trips a false alarm. Both are asserted in --self-test rather than
chased, because the adversary here is a local model answering a question, not
someone crafting a bypass, and each separator fix opened the next hole. The
false alarm errs in the safe direction: it turns the control red and gets
looked at, where a miss would be published as a passing score.

Verdicts were identical across four runs. Only avg_ms moved.

constraint:prefix is the one task still wrong WITH history: told "every reply

Restating the constraint as a scaffold was built, measured and removed. It
changed nothing: 21/22 with and without, identical in every domain, at a cost
of ~12 extra prompt tokens. Extraction was not the problem — it pulled exactly
"Every reply must start with the word CHECKED." and built a correct fragment.

Why the scaffolds TESTED could not fix it (3/3 reproducible, temperature 0).
Three layouts against one model snapshot cannot support "no scaffold can", and
an earlier draft of this document claimed exactly that:

  constraint on the SAME LINE as the question   FOLLOWS  FOLLOWS  FOLLOWS
  separated by a blank line                     ignores  ignores  ignores
  separated by one newline                      ignores  ignores  ignores

On this model snapshot the format constraint was honoured only when it sat
inline in the same sentence flow as the ask. A scaffold is a separate block by
construction, so every scaffold tested was defeated by the thing that makes it
a scaffold. That is a measured result on one model, not a proof about all
scaffolds. Position was not the
issue either: system and prompt placement both ignored.

This also explains why the CLINICAL scaffold works (7/10 -> 10/10) while these
did not. That one asks for CONTENT COVERAGE — "include a data collection
section" — and the model complies from a separate block. Format adherence is a
different capability, and this model does not have it at block distance.

Treat constraint:prefix as a documented model limitation, not a product bug.
Do not chase it by moving text onto one line: that overfits a quirk which will
not survive a model update, and it would not generalise.
